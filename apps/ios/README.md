# `@homerun/ios`

The iPhone app of [`docs/design.md` §9.8](../../docs/design.md#98-the-ios-app-a-full-conversational-client), milestone 10b. It is
a full conversational client for your desktops: threads and history, live chat, steering and
stopping, questions and approvals, new chats, and pushes you can answer from the lock screen. It
runs no agent. The views are React Native on [`@homerun/app-state`](../../packages/app-state/README.md)
over [`@homerun/remote`](../../packages/remote/README.md)'s relay transport, like the
[web client](../web/README.md). Keys, tokens, pushes and Face ID are native Swift.

## What an iPhone may do

The desktop decides, whatever the app does (§9.9, §13):

- An iPhone the desktop verified with **App Attest** (§18 rows 84, 99) has the `ios` role. It can
  answer questions and approvals, edit tasks, and allow destructive calls, but only with a Face ID
  signature the desktop checks (§18 row 115). Its cards say *Confirm with Face ID*.
- An iPhone the desktop couldn't verify (a simulator, a failed attestation) is treated as a
  browser, with the web client's reduced authority. Its cards say *Approve on your phone or Mac*,
  and the desktop's Settings lists it as an unverified iPhone.

## Layout

```

src/
  session.ts           IosSession: sign-in, registering this phone, pairing by QR, linking by
                       code, the desktops, push tokens, notification taps, sign-out, deletion
  attest.ts            App Attest for registration and each desktop, and Face ID key renewal
  adapters.ts          @homerun/remote's seams over the native module: account, keys, state
  cache.ts, sqlite.ts  the encrypted history cache (SQLCipher)
  lock.ts              the optional Face ID lock on open
  coalesce.ts          one render per 120 ms for a streaming reply
  selftest.ts          the protocol vectors under Hermes, for the simulator job
  polyfills.ts, uuid.ts  getRandomValues and randomUUID for Hermes
  config.ts, native.ts the build's configuration; the native module as the session sees it
  ui/                  the views: front door, threads, chat, input cards, inbox, settings
modules/homerun/       the local Expo module
  index.ts             its JavaScript interface
  ios/Bridge/          the Expo module and the notification delegate (lock-screen answers)
  ios/HomerunKit/      a Swift package: Noise, sealed messages, pushes, wire signing, OIDC,
                       the Keychain, App Attest and the approval key; `swift test` runs the vectors
targets/NotificationService/  the Notification Service Extension
scripts/hermes-vectors.ts     compiles the self-test with hermesc
test/                  bun tests: the session end to end, the cache, the helpers
```

`ios/` is generated by `expo prebuild` and never committed (§18 row 118).

## Keys, tokens and storage

- **The device keys** (§12): X25519 for Noise and Ed25519 for the relay, made by CryptoKit and kept
  as Keychain items marked `AfterFirstUnlockThisDeviceOnly`, in the group the app shares with its
  extension (`NMJBY8WL8T.com.angilyu.homerun.shared`), so the extension can open pushes on a locked
  phone. They are wrapped by a Secure Enclave P-256 key where the phone has one (§18 row 120).
  JavaScript never sees them: it asks the native module to `dh` and `sign`.
- **The approval key**: a Secure Enclave P-256 key that signs only after Face ID
  (`.biometryCurrentSet`), attested with the device keys. A new Face ID enrolment destroys it; the
  app makes another and renews it with each desktop by an App Attest assertion (§18 rows 115–116,
  121).
- **Sign-in** (§10.4, §18 row 119): OpenID Connect with PKCE in Swift, in an ephemeral
  `ASWebAuthenticationSession` that returns to `com.angilyu.homerun.ios:/auth/callback`. The
  refresh token stays in the shared Keychain; JavaScript only gets access tokens. Sign in with
  Apple is on the provider's page.
- **The history cache** (§18 row 122): SQLCipher through `expo-sqlite`, keyed from the app's own
  Keychain group (`WhenUnlockedThisDeviceOnly`), in a file under Data Protection class Complete.
  It holds each desktop's thread list and the newest events of each opened thread, so the app opens
  to readable history offline.
- **Someone else signing in**, or unpairing the last desktop, starts the phone again as a new
  device; signing out first drops its push token at the relay (§18 row 123). The first launch
  after an install clears what a deleted copy left in the Keychain.

## Pushes and the lock screen

The Notification Service Extension opens each sealed push with HomerunKit and CryptoKit, using the
device key and the pinned desktops from the shared Keychain (§9.7, §18 rows 71, 88). Anything that
doesn't open shows the generic *You have a new update*. A push's buttons are registered as a
category named after them (§18 row 125); each needs the phone unlocked. A button sends its answer
as one sealed HTTPS POST to the relay, from Swift, with no JavaScript and no live session. A
destructive approval has no buttons: tapping it opens the app for Face ID. When a request is
answered elsewhere, its push is replaced by a silent *Answered* (§18 row 117). The extension never
logs anything: what it handles is the plaintext.

## Offline

The cached history stays readable. A message to a thread while the Mac is away is sealed at the
relay and says *Will send when your Mac is back — expires in 12 h* (§18 row 107). Questions and
approvals say they can be answered when the Mac is back. New chats wait for the Mac (§18 row 128).

## Configuration

What the app connects to is fixed when it is built, from the environment of `expo prebuild` and
the Metro bundle:

| Variable | Meaning |
| --- | --- |
| `HOMERUN_IOS_RELAY_URL` | The relay, `https://…` |
| `HOMERUN_IOS_OIDC_ISSUER` | The identity provider's issuer URL |
| `HOMERUN_IOS_OIDC_CLIENT_ID` | Its public client id |
| `HOMERUN_IOS_AUTH_PARAMS` | JSON, extra authorization parameters (WorkOS: `{"provider":"authkit"}`) |
| `HOMERUN_IOS_DEV=1` | A development build: the development APNs and App Attest environments, the dev client's URL scheme, and plain `http` to the local network for a local relay and issuer |
| `HOMERUN_IOS_BUILD` | The build number (default 1) |

Without the relay, the issuer or the client id, the app says it isn't configured. A Release build
registers no URL scheme and allows no plain `http` (§18 row 124).

## Development

You need Xcode 26.4 or later (Expo SDK 57's precompiled modules are built with Swift 6.3; with an
older Xcode, set `EXPO_USE_PRECOMPILED_MODULES=0` before `pod install`), an iOS 26 simulator
runtime, and CocoaPods.

```sh
pnpm install
export HOMERUN_IOS_RELAY_URL=… HOMERUN_IOS_OIDC_ISSUER=… HOMERUN_IOS_OIDC_CLIENT_ID=…
HOMERUN_IOS_DEV=1 pnpm --filter @homerun/ios prebuild     # writes apps/ios/ios
(cd apps/ios/ios && pod install)
pnpm --filter @homerun/ios ios                            # builds, installs and starts Metro
```

Against a local relay and issuer, use loopback URLs: the simulator shares the Mac's network. A
simulator has no App Attest or Secure Enclave, so it pairs as a browser (above). On a device,
Xcode signs automatically with team `NMJBY8WL8T`.

## HomerunKit

`modules/homerun/ios/HomerunKit` is a Swift package compiled into both the app (through the local
module's podspec) and the extension, from the same sources. It ports `packages/protocol`'s Noise,
sealed messages, push presentation and wire signing to CryptoKit, and adds the Keychain, the OIDC
token owner, App Attest and the approval key. Its tests read `packages/protocol/vectors/*.json`
directly ([`packages/protocol`](../../packages/protocol/README.md#test-vectors)).

## Tests

```sh
pnpm --filter @homerun/ios typecheck
pnpm --filter @homerun/ios test          # bun: the session, the cache, the helpers (about 2 s)
pnpm --filter @homerun/ios test:hermes   # the self-test bundle compiles under hermesc -Werror
pnpm --filter @homerun/ios test:swift    # swift test in HomerunKit (macOS)
```

The session tests run `IosSession` against the real runtime, the relay's Bun adapter, the local
issuer and the mock APNs (`apps/homerund/test/remote/harness.ts`), with a fake native module whose
App Attest uses the test CA. They sign in, pair by QR with App Attest, receive pushes, allow a
destructive call with Face ID, renew the approval key, pair without App Attest as a browser, link
a second desktop by code, open a tapped notification, start afresh as a new device, and delete the
account.

CI (§18 rows 129–130): `ios-js` in `ci.yml` runs the first three on Linux for every pull request.
`ios.yml`'s `ios-swift` runs `swift test` on macOS when the Swift or the vectors change. Its
`ios-sim` runs nightly and on demand: a Release simulator build, then the app launched with
`-HomerunSelfTest 1`, which runs the protocol vectors under Hermes and prints
`HomerunSelfTest vectors: N passed` to the log. There are no Detox or Maestro tests yet (§17).

## Manual checks

These need a real iPhone, Apple's portals, a person, or all three. They continue the
[desktop's list](../desktop/README.md#manual-checks). Use a TestFlight build against the production
relay and WorkOS unless a step says otherwise. None of them submits to the App Store.

**The iPhone app (milestone 10b)**
37. **Apple Developer.** The App ID `com.angilyu.homerun.ios` has Push Notifications and App
    Attest, and `com.angilyu.homerun.ios.NotificationService` exists. Xcode's automatic signing
    creates both on the first device build; check them under Certificates, Identifiers &
    Profiles. The keychain groups need no registration: they use the team prefix.
38. **App Store Connect and TestFlight.** Create the app record for the bundle id (no
    submission). Build with the production variables, without `HOMERUN_IOS_DEV`, then
    `pnpm --filter @homerun/ios prebuild`, `pod install`, and open `apps/ios/ios/Homerun.xcworkspace`.
    Product → Archive, then Distribute App → TestFlight Internal Only. Install it from
    TestFlight.
39. **Export compliance.** Answer it in App Store Connect for that build: standard algorithms
    only (X25519, ChaChaPoly, SHA-256, Ed25519, P-256, TLS), the mass-market exemption. Then add
    `ITSAppUsesNonExemptEncryption: false` to `app.config.ts`'s `infoPlist` (§17 item 13).
40. **WorkOS for the iPhone.** Add the redirect URI `com.angilyu.homerun.ios:/auth/callback`,
    and turn on the Apple connection. Sign in on the phone: the sheet is private (no Safari
    cookies), *Sign in with Apple* is offered, and the app shows the front door after sign-in.
    Quit and reopen the app: still signed in.
41. **Pair by QR.** On the Mac, Settings → *Remote access* → **Pair a phone**; scan it in the
    app. The Mac's Settings lists the iPhone with Face ID approvals, not as unverified. Link a
    second Mac by code: its alert names the iPhone with the same six digits. Switch between the
    two in the app.
42. **Pushes, on a locked phone** (the relay with the production APNs key, §9.7). Ask for
    something that needs a question, then an approval of a write, then a destructive command:
    - each arrives with its real text, not *You have a new update*;
    - the question's options and the write's Approve/Deny work from the lock screen after
      unlocking, and the run continues on the Mac without opening the app;
    - the destructive approval has no buttons, and tapping it opens the app at the card;
    - answer a pushed request on the Mac: the push turns into a silent *Answered*;
    - a question over about 3 KB arrives as *You have a new update* and opens the app.
43. **Face ID.** Allow the destructive command: Face ID appears, and the run continues.
    Cancel Face ID: nothing is sent. Add an alternate appearance in Settings → Face ID, then
    allow another: the app renews its key, and the Mac posts *Face ID approvals changed*.
44. **Offline.** Quit Homerun on the Mac. The app says the Mac is offline; a message to a
    thread says *Will send when your Mac is back — expires in 12 h*, and *New chat* waits. Open
    Homerun: the message arrives once. In airplane mode, reopen the app: the thread list and
    opened threads are still readable.
45. **The lock on open.** Settings → *Lock with Face ID* (Face ID to turn on). Leave the app for
    a few seconds: no lock. Leave it for over a minute: locked. Turning it off takes Face ID.
46. **Deleting the account from the phone.** Make a throwaway account, pair it, then Settings
    → *Delete account* → Face ID. The app returns to sign-in, the Mac is signed out, the user is
    gone in the WorkOS dashboard, and *Sign in with Apple* under the Apple ID's settings no
    longer lists the app (§17 item 10).
